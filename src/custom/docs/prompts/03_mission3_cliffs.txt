미션 3 절벽 코스 구현 개선
=============================================

당신은 ROS 2 휴머노이드 대회 팀의 구현 담당자다. 아래 담당 미션을 실제 코드 수정과 시뮬레이터 검증까지 진행해라. 계획만 제시하고 끝내지 마라.
내 이니셜: [INI]  — 사용 전에 실제 이니셜로 바꾼다.

프로젝트와 작업 시작
- 저장소: https://github.com/imtaebin83-debug/RAI-301.git
- 작성 시 확인한 main: e48a9a1b59234f11714bbe1d47056c36379fd00b. 이 SHA로 고정하지 말고 작업 시작 시 최신 origin/main과 변경된 규칙·코드를 다시 확인한다.
- 먼저 README.md, src/custom/README.md, src/custom/docs/VALIDATION_REPORT.md, TEAM_OPTIMIZATION.md, 관련 미션·공통 코드와 공식 판정을 읽어라. 이 프롬프트의 과거 상태보다 최신 소스·규칙을 우선한다.
- Ubuntu는 aril@100.77.17.47(Tailscale), 기준 저장소 /home/aril/RAI-301, Conda는 /home/aril/miniconda3의 haic_rai301이다. rai-gpu 별칭은 이 PC에 실제 설정돼 있을 때만 쓴다. 비밀번호·개인키·API 키를 채팅이나 Git에 남기지 않는다.
- 원본 공유 폴더에서 branch 전환·reset·clean·pull로 다른 사람 작업을 덮어쓰지 않는다. 상태와 기존 worktree를 확인한 뒤 origin/main에서 본인 전용 opt/m3-이니셜-고유번호 브랜치와 /home/aril/rai-worktrees/이니셜-m3-고유번호 worktree를 만든다. 로컬 노트북에서도 별도 clone/worktree를 쓴다.
- 내 worktree의 src가 실행·import되는지 HAIC_ROOT, PYTHONPATH, cwd, __file__로 확인한다. Conda activation hook이 원본 경로를 가리킬 수 있으므로 확인 없이 원본 코드를 실행하지 않는다. 기존 가중치는 읽기 전용으로 재사용하거나 custom/tools/download_models.py로 준비한다.
- 공통 Conda 환경·전역 설정을 임의로 업그레이드하지 않는다. 추가 의존성이 필요하면 개인 환경에서 시험하고 제출용 의존성 변경안을 함께 남긴다. SSH나 GPU가 준비되지 않아도 가능한 소스 분석·구현·오프라인 검사를 계속하고, 실제 검증 대기 항목을 구분한다.

대회 규칙과 인터페이스
- 최종 실행 코드·필수 모델·의존성은 src/custom/ 안에 둔다. 조교 관리 main.py, mission_api.py, referee.py, main_config.yaml, scenarios/, ros2_bridge/, environment/, setup/는 읽기만 한다. 센서·보행 설정과 공유 의존성은 통합 담당자와 조율한다.
- 목표·색은 대회 명령에서 planner가 self.params로 넘긴 값을 쓴다. 미션 코드가 시나리오·정답 파일·referee 내부 상태·gt /odom으로 위치나 숨은 물체·방 배치를 알아내면 안 된다. 평가 하네스만 별도로 시나리오 생성과 공식 결과 확인을 수행한다.
- 미션 제어에서 self.randomize(), self.judge()를 호출하지 않는다. 채점·초기화·배치 편의 기능으로 수행 과정을 생략하지 않는다.
- begin_mission()은 G1을 이동시키지 않는다. e48a9a1의 selected.pos/yaw_deg는 실제 현재 자세가 아닌 미션 지정 자세였으므로 현재 위치로 재초기화하지 않는다. 공통 bringup의 연속 센서 추정과 허용된 실제 리스폰 처리를 사용한다.
- MissionN 클래스·MISSION·run()·self.result()와 Navigator 공개 인터페이스를 보존한다. 미션 파일에서 ROS init/spin/shutdown, 입력 대기, 무한 대기를 추가하지 않는다. 모든 센서·모델·제어 대기에 시간 상한을 두고 예외·종료 시 정지한다.
- 미션 4는 실제 VLM, 미션 5는 팀이 학습한 정책이 필수다. 규칙 기반 대체 경로를 해당 요구사항을 충족한 것처럼 보고하지 않는다.

협업과 공유 GPU
- 담당 범위 외 미션을 덮어쓰지 않는다. 공통 위치 추정·Navigator·bringup·planner는 미션 1/통합 담당자가 관리한다. 변경이 필요하면 재현 로그와 최소 변경안을 experiments/이니셜/m3/DEPENDENCY_REQUEST.txt에 남기고 담당자에게 전달할 자료로 정리한다. 독립적인 담당 작업은 계속한다.
- vision.py의 frame/_image/observe/Detection은 미션 2·6 공유 영역이다. 담당 함수의 변경과 공통 변경을 구분하고, 공통 부분을 바꾸면 두 미션의 회귀 검증이 필요하다.
- 다른 사람의 프로세스를 종료하거나 장치를 재부팅하지 않는다. GPU 점유·시뮬레이터·학습 프로세스를 확인하고 예약 순서대로 쓴다.
- 일반 시뮬레이터는 src에서 bash custom/tools/run_sim.sh --headless --missions 3 --no-wait로 실행한다. wrapper가 /tmp/rai-gpu-simulator.lock을 사용한다.
- randomized_suite.py, web_smoke.py, 별도 GPU 학습처럼 wrapper를 거치지 않는 GPU 작업은 같은 lock을 바깥에서 한 번 획득한다. 예: flock -n /tmp/rai-gpu-simulator.lock python custom/testing/randomized_suite.py ... . lock을 이미 잡은 wrapper를 다시 감싸거나 다른 사람의 시뮬레이터에 제어 명령을 보내지 않는다. CPU 분석·단위 검사는 병렬 진행할 수 있다.
- experiments/이니셜/m3/실행ID/에 작은 설정·측정값·실패 기록을 남긴다. 큰 데이터·가중치는 일반 Git에 올리지 말고 재현·전달 방법을 명시한다. 제출 시 필요한 가중치는 custom 내부에 실제로 포함돼야 한다.

진행과 완료
1. 현재 구현과 공식 실패 로그를 읽고, 재현 가능한 병목과 가설을 정한다. 필요한 논문·공식 구현을 선별해 확인하고 적용 이유를 기록한다.
2. 기존 baseline을 동일 조건에서 먼저 측정하고 작은 변경을 하나씩 비교한다. 성공 미션 수·안정성을 먼저 확보하고 시간을 줄인다.
3. 기본 시나리오뿐 아니라 별도 개발 seed와 손대지 않은 평가 seed, 다른 초기 위치·이전 미션 종료 위치를 구분해 시험한다. 기본 시작점으로 강제 리셋한 단독 시험을 연속 미션 성공으로 표현하지 않는다.
4. 필요한 단위·수치 검사와 실제 원본 referee 판정을 모두 확인한다. 기존 검사 46개는 출발점이며, 최신 main에서 검사 수·내용을 다시 확인한다. 단일 PASS·학습 loss·추정 좌표만으로 대회 성공을 선언하지 않는다. 무관한 전체 검사를 매번 반복하지 않는다.
5. 변경 파일, 기반/결과 커밋, 가설, 개발/평가 조건, 실제 PASS/시도 횟수와 시간, 실패 단계, 공식 JSON·로그, 의존성과 실행 명령, 공통 변경 요청을 src/custom/docs/experiments/이니셜_m3_날짜.md에 기록한다.
6. 충분히 검증한 담당 변경을 커밋하고 본인의 opt 브랜치만 push한다. main 자동 병합·force push·타인 브랜치 수정은 하지 않는다. 인증이 막히면 커밋·patch·보고서를 먼저 완성하고 필요한 로그인만 요청한다.
7. 최종 응답은 달라진 점, 실제 측정 결과, 남은 실패 원인, 팀원이 재현할 명령, 브랜치/커밋을 짧게 보고한다. 실제 실행하지 못한 검증은 명확히 표시한다.

담당 미션 작업 지시
--------------------
담당 범위
- src/custom/mission_3/와 그 아래의 미션 전용 보조 모듈.
- 공통 위치 추정·Navigator 수정은 통합 담당자에게 재현 자료와 최소 변경안으로 요청한다. 미션 안에 별도 이동 기반을 복제해 다른 좌표계를 만들지 않는다.

출발 상태와 목표
- 제공 보행 정책과 README의 공개된 바닥 통로를 따라가는 초기 경로가 있다.
- 초기에는 추락했고, 최종 시험은 위치 추정 손실 후 제한적 센서 복구가 중단돼 53.8초 FAIL이었다. 입구→출구 통과는 아직 성공하지 못했다.
- 틈 위치·폭과 문 좌표는 공개 정보다. 이를 경로 prior로 쓸 수 있으나 로봇의 실제 자세와 바닥 안전성은 센서로 확인한다.

우선순위
1. 로그·RGB-D·LiDAR·추정 자세를 비교해 첫 실패가 어디서 시작되는지 재현한다. 경로 폭, 몸/발의 여유, 회전 시 점유 공간, 드리프트, 추락·리스폰 처리를 나눠 측정한다.
2. 공개 통로를 기초로 바닥 가장자리/구멍과 안전한 통과 폭을 센서로 확인하고 보수적인 속도·정렬·waypoint를 구현한다.
3. 추락 또는 위치 손실 시 진행을 계속하지 말고 현재 상태를 확인한다. 실제 허용된 리스폰 이벤트와 횟수를 처리하고, 복구 가능할 때 입구부터 다시 접근한다.
4. 추락 허용 횟수·판정 영역·referee를 바꾸지 않는다. 공개된 waypoint에 도착했다고 가정한 pose reset이나 gt 좌표 사용은 금지다.
5. 제공 보행 정책으로 가능한 바닥 경로부터 검증한다. 새 보행·점프 정책이 꼭 필요하면 그 필요성을 실험으로 보이고 별도 학습/인터페이스/자원 계획을 기록한다.

검증과 인계
- 입구 직전으로 외부 평가 도구가 배치한 시험과, 복도·이전 미션 종료 위치부터 걸어오는 시험을 구분한다.
- 실제 입구→출구 순서와 원본 PASS, 추락 횟수, 시간, 중단·복구 이유를 기록한다.
- 반복 실행에서 어디까지 안정적인지 구간별로 보고하고, 실패가 공통 위치 추정에 있으면 센서 캡처와 함께 통합 담당자가 재현할 자료를 남긴다.
